# Musicianship Lab: agent guide

Read this file before changing the repository. It is the concise engineering guide; detailed product behavior lives in [`docs/PRODUCT.md`](docs/PRODUCT.md), and durable product rationale lives in [`docs/DECISIONS.md`](docs/DECISIONS.md).

## Product stance

Musicianship Lab is a practical, browser-based collection of keyboard and guitar tools for chord fluency, triads, inversions, voice leading, fretboard knowledge, MIDI identification, and saving useful harmonic discoveries. Favor actions that help someone play, hear, write, arrange, or practice music. Do not add speculative tools or navigation placeholders.

When documents and behavior disagree, inspect `outputs/index.html` and the regression suite, then update the documentation in the same change.

## Repository structure

- `outputs/index.html` — source of truth for the complete application: markup, CSS, theory data, state, rendering, event handling, persistence, migrations, and startup.
- `tests/voice-leading.test.js` — dependency-free Node regression harness for the entire application, despite its historical filename.
- `docs/PRODUCT.md` — current user-facing tools, navigation, conventions, MIDI behavior, persistence, and known limitations.
- `docs/DECISIONS.md` — meaningful product and architecture decisions with rationale.
- `README.md` — human-facing local-use and publishing overview.
- `package.json` — command runner; there are no package dependencies.
- `deployment.config.json` — canonical repository name, Pages base path, public URL, and physical direct routes.
- `scripts/build.mjs` — validates and copies the source into generated `dist/` output.
- `scripts/serve.mjs`, `scripts/static-server.mjs` — dependency-free local server.
- `scripts/check-pages.mjs` — verifies the generated Pages artifact and direct routes.
- `.github/workflows/deploy-pages.yml` — GitHub Pages build, test, verification, and deployment workflow.
- `dist/` — generated and ignored; never edit it as source.

## Architecture

The product is a dependency-free static application: plain HTML, CSS, and browser JavaScript in one self-contained file. There is no framework, bundler, backend, account system, database, external service API, external asset, or third-party font. Node 20 or newer is used only for local commands and verification.

The inline script is a strict-mode IIFE with shared mutable module state. It exposes a frozen `MUSICIANSHIP_ENGINE` and a broad `window.__voiceLeadingTrainerTests` interface. Both are intentional shared seams; renaming or removing test exports can break the harness even when the visible UI still loads.

Retained legacy modules include the editable timed Triad Trainer, the two-stage Keyboard Voice-Leading engine, standalone Fretboard Practice, former Key Study logic, old route IDs, storage keys, and migrations. They are hidden from current top-level navigation but remain tested or reused. Trace call sites and tests before altering them.

## Commands

No `npm install` is required.

```sh
# Local source server: http://127.0.0.1:4173/
npm run dev

# Full Node regression suite
npm test

# Focused early-exit scopes
MUSICIANSHIP_TEST_SCOPE=triad-shapes node tests/voice-leading.test.js
MUSICIANSHIP_TEST_SCOPE=progression-builder node tests/voice-leading.test.js

# Optional compact fretboard renderer preview
node tests/voice-leading.test.js --render-fretboard-preview

# Generate dist/
npm run build

# Preview at http://127.0.0.1:4173/musicianship-lab/
npm run preview

# Build, test, and validate the Pages artifact
npm run verify
```

`npm run check:pages` assumes `dist/` already exists. Opening `outputs/index.html` directly is supported, but use HTTP for routing, pointer/focus/layout, permissions, origin, and Web MIDI checks.

The Node harness supplies a synthetic DOM, timers, localStorage, location, and optional MIDI navigator. It is not a layout engine or a real browser. Do not describe harness-only verification as browser verification.

## GitHub Pages

- Repository: `lighthousedesigns/musicianship-lab`
- Git remote: `https://github.com/lighthousedesigns/musicianship-lab.git`
- Default branch: `main`
- Project base path: `/musicianship-lab/`
- Configured public URL: `https://lighthousedesigns.github.io/musicianship-lab/`
- Canonical configuration: `deployment.config.json`

The workflow runs on pushes to `main` and manual dispatch. It uses Node 24 to build, run the regression suite, validate Pages paths, upload `dist/`, and deploy through the `github-pages` environment. It needs only `contents: read`, `pages: write`, and `id-token: write`; do not add secrets. The repository must use **Settings → Pages → Build and deployment → GitHub Actions**.

This is a project site. Asset and link paths must be relative or explicitly honor `/musicianship-lab/`; never assume the domain root `/`. The build rejects new root-relative JavaScript, CSS, image, font, and CSS `url()` references.

Physical direct routes currently generated by the build are:

- `/musicianship-lab/keyboard/chord-practice/`
- `/musicianship-lab/fretboard/voice-leading/`
- `/musicianship-lab/fretboard/triad-shapes/study/`
- `/musicianship-lab/fretboard/triad-shapes/quiz/`

When adding a public direct route, update the route parser, `deployment.config.json`, and verification together. Query/hash routes remain supported. A successful artifact check does not prove live HTTP delivery, rendered layout, localStorage, or Web MIDI behavior.

## Critical do-not-break rules

- Preserve every working current tool, route, setting, migration, theory rule, renderer, accessibility behavior, and tested workflow unless the task explicitly replaces it.
- Edit `outputs/index.html`, never generated `dist/`, for application changes.
- Avoid unrelated refactors in the roughly 15,000-line monolith; shared state makes broad changes risky.
- Keep current navigation intentional: Keyboard opens directly into Chord Practice; Fretboard exposes Voice Leading then Triad Shapes; Explore exposes Chord Identifier and Favorite Chords.
- Do not restore retired Recognize Triads, Play the Chord, Keyboard Voice Leading, Fretboard Practice, standalone Key Study, or Fretboard Cycle navigation without an explicit product decision.
- Preserve stable exercise IDs, aliases, saved-state schemas, tolerant loading, and migrations. Browser storage failures must not make the current visit unusable.
- Keep MIDI optional wherever manual naming, reveal, study, or navigation already works. Request MIDI permission only after an explicit user action.
- Preserve theoretical spelling supplied by the active key. Do not replace E-sharp, G-flat, or other correct spellings with convenient enharmonic shortcuts.
- Reuse shared theory, voicing, grading, diagram, TAB, navigation, MIDI, and persistence implementations. Do not create parallel versions of the same musical rule.
- Trace every consumer before changing a shared renderer. Piano diagrams serve Chord Practice prompts and answers. Fretboard diagrams serve legacy Practice, Shape Library, Voice Leading route/detail cards, and Triad Shapes Study/Quiz.
- Keep noninteractive diagram consumers noninteractive when quiz markers are interactive.
- Preserve the Triad Shapes quiz marker `translate(-50%, -50%)` transform in its marker-specific `:active` rule; losing it moves the pointer target and can cancel clicks.
- Keep compact fretboard diagrams compact enough to show several route cards together; improve legibility through contrast and typography, not enlargement.
- Fretboard Voice Leading Starting Location defaults to Auto. Exact selection is deliberate only through Choose Exact Shape or Start Route Here. Stale or incompatible saved state must recover to Auto.
- Auto route generation may substitute a valid starting inversion and update the visible selection. Do not block when a valid physical route exists.
- Switching between Fretboard Route and Shape Library must preserve a valid current route and shared musical settings.
- Do not silently change a selected key, chord, inversion, string set, fret range, exact shape, custom set, or progression.
- Chord Identifier is heuristic. Preserve alternate candidates and uncertainty instead of forcing a single interpretation.
- Preserve real accessible controls, focus movement, live feedback, keyboard activation, and reduced-motion behavior.

## Verification expectations

Before changing behavior, inspect the relevant markup, state, handlers, persistence, migrations, shared engines/renderers, call sites, and tests. For a small isolated change, run the focused scope while iterating. Run `npm test` for shared or substantial changes and `npm run verify` for deployment-sensitive work.

Use a real browser for behavior involving pointer geometry, focus, computed CSS, responsive layout, URL delivery, localStorage origin, browser lifecycle, or Web MIDI. For public-release confidence, check the home page, query and physical direct routes, diagrams, TAB, controls, responsive layout, persistence, and MIDI permission/device behavior over HTTPS.

Every completion report should state:

- files changed
- behavior changed, or explicitly that behavior is unchanged
- persistence or migration effects
- tests added or updated
- exact commands and results
- real-browser checks performed or omitted
- known limitations or unverified behavior

## Decision priority

When implementation details conflict, prioritize:

1. get the user into meaningful practice quickly
2. preserve musical correctness and explicit spelling
3. preserve working behavior and compatible saved state
4. keep the interface clear and direct
5. reuse shared engines and renderers
6. retain advanced controls without burdening the default workflow
